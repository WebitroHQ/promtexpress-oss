# Evals

`scripts/validate-library.mjs` proves a template is well-formed. Evals check what a template actually produces.
This folder defines the format and the first suites. Calling live models, a model judge and the daily canary are
follow-up work tracked in [#17](https://github.com/WebitroHQ/promtexpress-oss/issues/17).

```
library/evals/<modality>/<slug>/
├── suite.json                   what is required: cases, checks and thresholds
└── recorded/
    ├── <run-id>.json            what was measured: configuration and one output per sample
    └── <run-id>.scores.json     per-sample, per-check scores for that run (generated)
```

## Check locally

```bash
node scripts/eval-library.mjs            # validate, re-score recorded outputs, fail if stored scores are stale
node scripts/eval-library.mjs --write    # regenerate scores after changing a check or threshold on purpose
```

No install and no API keys: scoring runs over the recorded outputs.

## suite.json

```json
{
  "format": 1,
  "template": "code/sql-query-from-question",
  "samples": 5,
  "cases": [
    {
      "id": "null-discount-as-zero-sqlite",
      "description": "A nullable column the question says to treat as zero.",
      "variables": { "question": "...", "schema": "...", "dialect": "SQLite" },
      "checks": [
        { "name": "no-select-star", "type": "not-matches", "pattern": "SELECT\\s+\\*", "flags": "i" },
        { "name": "has-required-sections", "type": "contains-all", "values": ["Assumptions", "SQL Query", "Explanation"], "minScore": 1 }
      ]
    }
  ]
}
```

- **`id` and `name` are stable identifiers.** Write them by hand and keep them when you edit the case text or the
  check. Recorded runs and scores are paired on them, so a changed id would look like a deleted case plus a new one.
  The runner rejects a recorded case whose id is no longer in the suite, so a rename breaks loudly instead of silently.
- **Thresholds live only here.** `minScore` (default `1`) is part of the suite, never part of a run or its scores.
  Changing a threshold shows up as a change in the regenerated scores rather than rewriting what was measured.
- `samples` is how many samples a live run records per case.
- `variables` must be declared by the template, and every required template variable must be set.

| Check type | Parameters | Score | Precision |
|---|---|---|---|
| `contains-all` | `values`, optional `ignoreCase` | share of `values` found in the output | 2 |
| `matches` | `pattern`, optional `flags` (`i`, `m`, `s`, `u`) | 1 if the regex matches, else 0 | 0 |
| `not-matches` | `pattern`, optional `flags` | 1 if the regex does not match, else 0 | 0 |
| `table-column-in-variable` | `column`, `variable` | share of non-empty cells in that Markdown table column that appear in the variable (quote marks, case and spacing ignored) | 2 |

A check passes when its score reaches `minScore`.

## Recorded runs

```json
{
  "format": 1,
  "id": "2026-09-15-hand-written-fixture",
  "suite": "code/sql-query-from-question",
  "recordedAt": "2026-09-15T00:00:00Z",
  "note": "Optional free text.",
  "config": {
    "provider": "fixture",
    "model": "hand-written",
    "temperature": null,
    "maxTokens": null,
    "templateVersion": "1.0.0",
    "templateSha256": "<SHA-256 of the template's template text>"
  },
  "cases": [
    { "id": "null-discount-as-zero-sqlite", "samples": [{ "output": "..." }, { "output": "..." }] }
  ]
}
```

- `config.model` is the exact model snapshot, never an alias. `temperature` and `maxTokens` are `null` only when they
  do not apply.
- Every sample keeps its own output, so the run can be re-scored under different checks later.
- The report opens each run with its configuration and whether the template text changed since the recording, before
  any score.

The runs committed today are hand-written fixtures (`"provider": "fixture"`), including deliberately flawed samples,
that prove each check catches what it claims. Real runs will come from the live runner.

## Scores

Generated by `--write`; do not edit them by hand. Every check result stores:

- `score`: a number, rounded to
- `precision`: the number of decimal places, and
- `pass`: decided when scoring, from the unrounded score and the suite's `minScore`. Readers use this field instead of
  re-deriving it from the rounded score, so two readers can never disagree at the boundary.

CI re-scores every recorded run and fails when the stored scores differ, so any change to a check, a threshold or a
recorded output is visible in the pull request.
